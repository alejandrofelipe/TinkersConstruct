## Design decisions (defaults; revisit if they fight the code)

- **D-target — 1.21.10 folding 1.21.9** (user, 2026-11-23): see the target decision above.
- **D-T — transfer API in two steps (user: "1 then 2").** Step 1 (Phases 1–2): **only what is required** — move capability **registration and lookup** to `Capabilities.Fluid/Item/Energy` and keep every handler implementation, helper and caller on the deprecated legacy interfaces. Step 2 (**Phase 6**, separate): full migration to `ResourceHandler`/transactions.
  - **D-T1 — decision (user, 2026-11-23, after Phase 0 found NeoForge ships only new → legacy bridges and removed the old capabilities): no legacy → new adapter.** **Registration:** every handler we register as a capability (Mantle's and Tinkers' ~34 registration sites — smeltery/table/gadget BEs, fluid items, tool capability provider) is **ported natively** to `ResourceHandler<FluidResource>` / `ResourceHandler<ItemResource>` / `EnergyHandler` in step 1 (transactions via NeoForge's own `SnapshotJournal`-based building blocks; item capabilities on `ItemAccess`). **Lookups** of other blocks/items use the NeoForge bridges (`IFluidHandler.of(level.getCapability(Capabilities.Fluid.BLOCK, pos, side))`, `IItemHandler.of`, `FluidResourceHandlerItemAdapter`; null-safe helper in Mantle), so consumer code can stay on the deprecated interfaces until Phase 6. Rationale: no throwaway adapter with approximate transaction semantics; what step 1 writes is what Phase 6 would write anyway.
  - **D-T2 — internal consumers of our own natively-ported handlers** (e.g. GUIs, renderers, melting/casting logic that read a tank) either call the new API directly where the code is already being touched, or go through `IFluidHandler.of(...)` on our own handler; prefer the direct call when it's a one-liner. Keep NBT/ValueIO layout identical (the M4 save-compat gametests guard it).
  - **D-T3 — tests:** port `CapabilityGameTests` to the new capabilities; add interop gametests: Tinkers tanks/drains/casting with a vanilla hopper and with NeoForge's `transfer.fluid.FluidUtil` bucket interaction, plus transaction semantics on our native handlers (simulate/abort leaves no side effect — casting tables and melters react to fills; commit applies once; nested abort).
- **D-JT — JSON Things re-added in Phase 5** (user): version pinned now (`0.16.0`), deps/maven/sources stay excluded until then.
- **D-IE — Immersive Engineering stays excluded** (user): still 1.21.1-only.
- **D1 — `isClientSide` rename is scripted:** regex `\.isClientSide\b(?!\()` → `.isClientSide()` over `src/**/*.java` in both repos (excluding string literals/comments by review of the diff), then compile. Same for `noCollission(` → `noCollision(`. One commit per repo, separate from logic changes.

## Known risks

- **Transfer step 1 ports our registered handlers natively (D-T1)** — the risk moves from adapter semantics to correctness of the new transactional handlers (simulate/abort must have no side effects; casting tables and melters react to fills). Covered by the D-T3 interop + transaction gametests; external mods see real transactions, no deferred execution.
- **Two-phase rendering breaks silently** (nothing drawn, wrong order, stale state when extract misses a field) — compiler and unit tests won't see it; the D8 side-by-side review is the gate. Render states must not hold BE references.
- **Event-based input breaks silently** where an override lost `@Override` — sweep (Phase 4) + a click/drag uitest scenario.
- Removed old capability objects mean **no mixed state compiles**: every registration and lookup must move in 1b/2B, even though implementations stay legacy.
- Crafting Tweaks was built against a Balm 21.10.2 snapshot — runtime mismatch possible with 21.10.11.
- JSON Things 0.13.7 → 0.16.0 spans three MC versions of API drift (M1-era re-add had 13 breaks).
- JEI 24 → 26 (two majors) — diff the API before touching the plugin.
- uitest needs an unlocked screen (`atio6axx.dll` GL init fails while Windows is locked).
