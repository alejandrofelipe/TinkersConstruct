## Design decisions — D-R1/D-R2, D-N1, D-N2 **confirmed 2026-11-26** (recommended options); D-P, D-ATLAS, D-REL stand as proposed

- **D-R1 — `ResourceLocation` → `Identifier` is scripted, per repo, in its own commit** (no logic change in that commit):
  1. Token swap `\bResourceLocation\b` → `Identifier` in every `src/**/*.java` (main, test, datagen), **including comments/javadoc** (`{@link ResourceLocation}` would otherwise break javadoc and mislead), imports `net.minecraft.resources.ResourceLocation` → `net.minecraft.resources.Identifier`. Word boundaries leave our own `*ResourceLocation*` names untouched. String literals: 0 real hits (the 8 regex hits are lines holding two strings) — reviewed in the diff.
  2. Same script: `ResourceLocationException` → `IdentifierException` (+ import `net.minecraft.IdentifierException`), `ResourceLocationArgument` → `IdentifierArgument`, `isAllowedInResourceLocation` → `isAllowedInIdentifier`, `readResourceLocation(`/`writeResourceLocation(` → `readIdentifier(`/`writeIdentifier(` (all hits are `FriendlyByteBuf` calls — confirm in the diff).
  3. **Compiler-driven** second pass: `.location()` → `.identifier()` only where javac reports `cannot find symbol method location()` on a `ResourceKey` receiver (line list from the flow-gate CSV); `TagKey`/`SoundEvent` keep `location()`.
  4. Static factories need no change (`fromNamespaceAndPath`, `parse`, `tryParse`, `tryBuild`, `withDefaultNamespace`, `CODEC`, `STREAM_CODEC` keep their names). JSON/data files don't change.
  5. Then compile; fix the remaining cascades by hand.
- **D-R2 — keep Mantle's (and Tinkers') public names** unless forced: `ResourceLocationLoadable`, `ResourceLocationSerializer`, `Loadables.RESOURCE_LOCATION`, `JsonHelper.getResourceLocation/parseResourceLocation/convertToResourceLocation`, `BookRepository.getResourceLocation`, fields/methods/params named `*location*`/`resourceLocation`. Rationale: zero behaviour value, large downstream churn, and backports to the 1.21.1–1.21.10 lines get harder with every renamed member. Forced renames only: overrides of renamed vanilla/NeoForge/JEI methods (JEI `getIdentifier`). Optional later cleanup (separate decision): add `Identifier`-named aliases and deprecate the old names.
- **D-N1 — `package-info.java` → JSpecify `@NullMarked`** (replaces both `@ParametersAreNonnullByDefault` and `@MethodsReturnNonnullByDefault`), scripted (79 Mantle + 278 Tinkers + the empty Tinkers one left alone), own commit. Evidence: vanilla and NeoForge 1.21.11 do exactly this; `jspecify:1.0.0` is on the compile classpath. Same meaning as the old pair (non-null unless `@Nullable`, now also for fields). Alternatives considered: keep jsr305 `@ParametersAreNonnullByDefault` and drop only the removed MC annotation (loses the return-value default, IDE warnings shift), or ship a Mantle copy of `MethodsReturnNonnullByDefault` (keeps a dead convention alive). `javax.annotation.Nullable` keeps working under `@NullMarked` (IntelliJ recognizes both).
- **D-N2 — jsr305 stays for M6 (no `@Nullable` migration forced).** It still compiles (NeoForm 1.21.11 libraries), so the `javax.annotation` imports (Mantle 235 files / 241 imports, Tinkers 905 / 926; `Nullable` in 151 + 614 files) stay untouched in Phases 1–2. Options for the user: (a) **recommended**: defer the JSpecify `@Nullable` migration (scripted import swap + fix type-use placement: `Outer.@Nullable Inner`, arrays `Object @Nullable []`, fully-qualified types) to an optional Phase 5b after the battery is green, or to M7 Phase 0 if NeoForm 26.x stops listing jsr305; (b) migrate in Phase 1/2 together with the rename (one big churn, more risk while debugging); (c) never migrate and add an explicit `compileOnly 'com.google.code.findbugs:jsr305:3.0.2'` when NeoForm drops it. Runtime is unaffected either way (missing annotation classes are ignored by reflection).
- **D-P — permissions:** `MantleCommand.PERMISSION_GAME_COMMANDS` / `PERMISSION_EDIT_SPAWN` (and `reducedDebugLevel`) become `PermissionCheck`s (`Commands.LEVEL_GAMEMASTERS` etc.), same names; callers use `requires(Commands.hasPermission(MantleCommand.PERMISSION_…))`; `Player#hasPermissions(int)` → `player.permissions().hasPermission(Permissions.COMMANDS_GAMEMASTER)` (or a Mantle helper). Mantle API change → documented in the migration guide. **R2 (vocabulary rule) — as implemented in 1b (Mantle `621bac0e`), superseding the `PermissionCheck` constants above:** the public `int` constants `MantleCommand.PERMISSION_*` stay unchanged (op level is a stable domain concept) and Mantle adds `MantleCommand.hasPermission(CommandSourceStack, int)` / `hasPermission(Player, int)` (1→`Permissions.COMMANDS_MODERATOR`, 2→GAMEMASTER, 3→ADMIN, 4→OWNER, ≤0 always, >4 never). Tinkers' 9 subcommands + `CreativeSlotItem`/`ModifierCrystalItem` switch from `sender.hasPermission(X)` / `player.hasPermissions(X)` to the helpers in Phase 2C and never name the vanilla permission types.
- **D-RT — render types:** Mantle/Tinkers custom types are rebuilt with `RenderSetup.builder(<the same RenderPipeline>)` + `RenderType.create`, keeping names, pipelines, textures, lightmap/overlay and outline flags 1:1; vanilla types via `RenderTypes`. Verify each type in uitest (fluids in GUI and world, smeltery fluid, casting fade `itemEntityTranslucentCull`, AOE outline `lines()`).
- **D-BQ — baked quads:** quad producers go through `FaceBakery.bakeQuad(partCache, …)` / NeoForge `QuadBakingVertexConsumer` where they exist today; hand-built quads use the record constructor with `ModelBaker.PartCache` vectors and NeoForge `BakedColors`/`BakedNormals` for per-vertex tint/normals; quad readers use `position(i)`/`packedUV(i)` (`UVPair.unpackU/V`) instead of `int[]` offsets. The removed `QuadTransformers` uses become `QuadTransforms.applyTransformation` or a small Mantle helper. Read vanilla `BlockModelWrapper`/`ItemModelGenerator` first and hand subagents a verified recipe (M3 lesson).
- **D-ATLAS — item atlas:** default proposal: textures that are block/fluid sprites stay on `LOCATION_BLOCKS`; item textures used by dynamic item models switch to `ModelManager.BLOCK_OR_ITEM` (vanilla's special case for materials that may be either) or to `LOCATION_ITEMS`; Tinkers keeps `item/tool/` in the blocks atlas only if a model must mix tool and block sprites in one quad list (otherwise move it to `items.json` and drop the duplicate). Decide per call site in 1c/2B after reading how vanilla 1.21.11 picks the item render type atlas; gate: client log has no missing-texture warnings + every item model in the uitest suite matches the 1.21.10 reference.
- **D-REF — verification gate = reference run** (M4/M5 lesson): Phase 4 uitest review side by side with a **1.21.10 reference run** from tags `v1.21.10-1.16` / `v1.21.10-3.15.0` in throwaway worktrees **outside** the workspace (`C:\Users\aleja\DEV\nt-ref-12110\{repo,tinkers}`; never under `New Tinkers/`), same suite, every PNG pair viewed, screen unlocked.

## Known risks

- **Item atlas split renders silently wrong** (missing texture, no exception at compile time; maybe a log warning) — D-ATLAS + the item-model uitest review vs the 1.21.10 reference are the gate.
- **`BakedQuad` rewrite in tool/fluid models** — wrong UV/normal/color packing shows only visually (dark faces, wrong tint, broken AO). Vanilla's 13-arg constructor silently defaults NeoForge's normals/colors/AO.
- **Custom render types** rebuilt on `RenderSetup` — a missing lightmap/overlay/texture binding or wrong pipeline compiles and draws black/invisible geometry.
- **The rename touches ~700 files**: script mistakes (receiver-blind `.location()`, comments/strings) would be hard to spot in review — keep the scripted commits pure and compiler-driven for receiver-dependent renames.
- **Parchment parameter names can be stale** for methods whose parameters were reordered (`Mth.clampedLerp`); trust call sites in vanilla over names.
- **`AbstractContainerScreen#keyPressed` returns `false` for unhandled keys** — Tinkers screens that chain on `super.keyPressed` may change behaviour (keys falling through to the game).
- **Mantle public API changes** (permission constants) ripple into Tinkers and any other downstream mod; document them.
- **jsr305 rides on NeoForm's library list** — gone the day NeoForm drops it (check at M7 Phase 0, NeoForm `26.1.2-x`).
- New JEI 27 deprecations (render/tooltip) — M5 left 0 `[removal]` warnings; keep it that way only if the replacements are straightforward (Phase 5).
- Crafting Tweaks compiled against Balm `21.11.2`, runtime Balm `21.11.9.1` — runtime mismatch possible (step Balm down within 21.11.x).
- uitest needs an unlocked screen (`atio6axx.dll` GL init fails while Windows is locked).
